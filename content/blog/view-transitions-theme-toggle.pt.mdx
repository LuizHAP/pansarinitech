## O que era

Até outubro de 2026 este site tinha um tema claro, um tema escuro e um botão no header para alternar entre eles. O clique não só trocava as cores. Ele usava a View Transitions API para revelar o novo tema como um círculo crescendo a partir do ponto clicado, até cobrir a página inteira.

O alternador não existe mais, nem o CSS e o componente que faziam ele funcionar. Mantive este post porque a técnica continua valendo: a detecção de feature, as duas camadas de movimento reduzido e o fallback de teclado servem para qualquer transição que você coloque dentro de um `startViewTransition`. O código abaixo é o que ficava no `globals.css` e no componente do alternador até o redesign.

## Suporte dos navegadores

A View Transitions API chegou ao Chromium 111 <InlineBadge variant="secondary">Chrome 111+</InlineBadge>, ao Safari 18 <InlineBadge variant="secondary">Safari 18+</InlineBadge> e ao Firefox 144 <InlineBadge variant="secondary">Firefox 144+</InlineBadge>. Isso cobre a grande maioria dos navegadores em 2026, mas "grande maioria" não é "todos." Recrutadores em um laptop corporativo desatualizado, ou com um celular sem atualização há um ano, recebiam a troca instantânea de tema que já existia antes de todo esse código entrar. Era progressive enhancement por design, não por acidente.

O bloco inteiro de View Transitions ficava dentro de um guard `@supports (view-transition-name: root)` no CSS e de uma detecção de feature explícita no handler JavaScript. Navegadores que não entendiam `startViewTransition` caíam no retorno antecipado e chamavam `setTheme` direto. Sem polyfill, sem shim, sem biblioteca de fallback. O comportamento que já existia era o fallback certo.

Escolhi a API porque o alternador de tema era o momento visualmente mais marcante do site. Toda outra interação era texto ou link. O toggle era o único lugar onde algo dramático acontecia, e uma revelação saindo do ponto do clique fazia a troca parecer consequência direta do clique.

## Como a revelação radial funcionava

O modelo mental por trás do `startViewTransition` é baseado em snapshots. Quando você chama `document.startViewTransition(callback)`, o navegador captura na hora um screenshot da página atual, o snapshot ANTIGO. Em seguida executa o callback, que aqui chamava `setTheme`. O DOM passava a refletir o novo tema. O navegador captura um segundo screenshot, o snapshot NOVO. Animações CSS controlam como a transição do ANTIGO para o NOVO acontece na tela.

O snapshot NOVO fica em cima do ANTIGO em um contexto de composição empilhado. O comportamento padrão do navegador faz um cross-fade de opacidade entre os dois em cerca de 250ms. Serve para a maioria das transições, mas fica lavado numa troca de paleta em que as duas superfícies têm fundo sólido. A revelação ficava embaçada.

Troquei o padrão por `clip-path`. O snapshot ANTIGO ficava totalmente visível e opaco, com `animation: none` em `::view-transition-old(root)`. O snapshot NOVO começava como um círculo de raio `0%` centralizado nas coordenadas do clique e crescia até `150%`, o suficiente para cobrir o viewport onde quer que o toggle estivesse. O novo tema entrava a partir do botão, não das bordas da tela.

O valor `150%` não era arbitrário. Na distância máxima entre um toggle num canto e o canto oposto do viewport, você precisa de pouco menos de 142% para garantir cobertura total em qualquer tamanho de tela. Arredondei para `150%` como margem segura.

## Configurando a animação clip-path

O CSS ficava no `globals.css` dentro de um guard composto: `@media (prefers-reduced-motion: no-preference)` envolvendo `@supports (view-transition-name: root)`. Os dois guards precisavam ser verdadeiros. Se o usuário preferisse movimento reduzido, este bloco não se aplicava e o bloco de fallback de movimento reduzido assumia (próxima seção).

```css
@media (prefers-reduced-motion: no-preference) {
  @supports (view-transition-name: root) {
    /* Snapshot ANTIGO fica parado; NOVO varre por cima. */
    ::view-transition-old(root) {
      animation: none;
      mix-blend-mode: normal;
    }
    ::view-transition-new(root) {
      animation: vt-reveal 420ms cubic-bezier(0.4, 0, 0.2, 1) forwards;
      mix-blend-mode: normal;
      z-index: 1;
    }

    @keyframes vt-reveal {
      from {
        clip-path: circle(0% at var(--vt-x, 50%) var(--vt-y, 50%));
      }
      to {
        clip-path: circle(150% at var(--vt-x, 50%) var(--vt-y, 50%));
      }
    }
  }
}
```

As propriedades customizadas `--vt-x` e `--vt-y` eram definidas pelo handler JavaScript logo antes de chamar `startViewTransition`. Os valores padrão (`50% 50%`) faziam com que, se o handler não as definisse, a revelação saísse do centro do viewport em vez de um canto, um fallback aceitável.

O override `mix-blend-mode: normal` nos dois pseudo-elementos era obrigatório. Alguns navegadores aplicam por padrão um blend mode não-normal ao snapshot ANTIGO, o que gera um artefato visível quando o ANTIGO fica sob um NOVO parcialmente transparente. Definir os dois como `normal` eliminava o artefato.

A duração de 420ms e o easing (`cubic-bezier(0.4, 0, 0.2, 1)` é o easing "standard" do Material Design) foram calibrados no olho em vários tamanhos de viewport. Mais rápido parecia apressado; mais lento parecia estado de carregamento, não transição.

## Fallback para movimento reduzido

<Callout type="info">Movimento reduzido não é preferência estética. É uma acomodação médica. Transtornos vestibulares (condições do ouvido interno que afetam equilíbrio e percepção espacial) podem ser desencadeados por movimentos grandes na tela. A revelação radial varria o viewport inteiro em 420ms. Para quem tem uma condição vestibular, isso não é um efeito sutil. O fallback de dois níveis veio de levar a sério a intenção do WCAG para `prefers-reduced-motion`: "reduzir, não necessariamente eliminar" o movimento.</Callout>

Implementei duas camadas de proteção para movimento reduzido, e as duas eram necessárias.

A primeira camada era JavaScript: se `window.matchMedia('(prefers-reduced-motion: reduce)').matches`, o handler chamava `setTheme` e retornava sem chamar `startViewTransition`. É a acomodação mais limpa possível. A maquinaria de snapshot nunca roda, nenhum pseudo-elemento é criado e a troca de tema é instantânea. Zero movimento, zero trabalho de GPU.

A segunda camada era CSS. O bloco de movimento reduzido que existia desde a Phase 1 aplicava `* { transition: none; animation: none }`. Esse bloco **não** alcança `::view-transition-old` e `::view-transition-new`. Esses pseudo-elementos vivem na shadow tree da UA e são invisíveis para o seletor universal. Sem um override explícito, um navegador que executasse `startViewTransition` tocaria o cross-fade padrão de ~250ms mesmo para quem pediu movimento reduzido.

A camada CSS era defesa em profundidade. Se a camada JavaScript falhasse (improvável, mas possível numa condição de corrida ou numa mudança futura de navegador), o fallback CSS mantinha a transição num fade de opacidade calmo de 200ms em vez de uma revelação do tamanho do viewport.

```css
@media (prefers-reduced-motion: reduce) {
  @supports (view-transition-name: root) {
    ::view-transition-old(root),
    ::view-transition-new(root) {
      animation: vt-fade 200ms linear forwards !important;
      mix-blend-mode: normal;
    }
    /* ANTIGO faz fade 1 → 0; NOVO faz fade 0 → 1 (reverso). */
    ::view-transition-new(root) {
      animation-direction: reverse !important;
    }
    @keyframes vt-fade {
      from { opacity: 1; }
      to   { opacity: 0; }
    }
  }
}
```

O `animation-direction: reverse` em `::view-transition-new` é a parte mais fácil de errar. `vt-fade` anima a opacidade de `1` para `0`. Aplicado na direção normal nos dois pseudo-elementos, o ANTIGO some e o NOVO também some, e o usuário fica olhando para o fundo de composição com os dois snapshots invisíveis por um instante. Inverter o NOVO faz ele animar de `0` para `1`, que é um cross-fade correto: o ANTIGO se dissolve enquanto o NOVO aparece.

## Troca entre paleta clara e escura

O alternador chamava `setTheme('dark')` ou `setTheme('light')`. Por baixo, o `next-themes` escreve ou remove a classe `.dark` no `<html>` em um tick síncrono e atualiza o `localStorage` ao mesmo tempo. Esse era o mecanismo inteiro. Nenhum re-render React na raiz era necessário.

O Tailwind v4 resolvia as variáveis CSS OKLCH sob a regra `@custom-variant dark (&:where(.dark, .dark *))`. Quando `.dark` chegava ao `<html>`, todos os descendentes adotavam a paleta escura: o fundo escuro, a cor primária própria dela e os tokens de texto ajustados. Quando `.dark` saía, a paleta clara voltava.

O mecanismo de snapshot de View Transitions capturava o estado visual antes e depois dessa troca de classe. O snapshot ANTIGO era a página clara inteira, o NOVO a página escura inteira, ou o contrário. A animação clip-path revelava o NOVO a partir do ponto do clique, então a nova paleta se espalhava de onde o toggle estava na tela.

O toggle era o momento mais elaborado de UX no site, e a revelação reforçava isso sem virar truque.

## O handler do toggle

A implementação completa do `onClick` é curta o bastante para percorrer em um bloco. Cada linha existia por um motivo que não era óbvio durante a implementação.

```tsx
const onClick = (event: MouseEvent<HTMLButtonElement>) => {
  const next = isDark ? 'light' : 'dark';

  // Detecção de feature (Safari <18 / Firefox <144 / Chromium antigo) E
  // bypass em prefers-reduced-motion (CSS cuida do fade visual; ignoramos
  // a maquinaria de snapshot para honrar a intenção "reduce" na camada JS).
  if (
    typeof document === 'undefined' ||
    !('startViewTransition' in document) ||
    window.matchMedia('(prefers-reduced-motion: reduce)').matches
  ) {
    setTheme(next);
    return;
  }

  // Captura das coordenadas do clique com fallback para teclado.
  // Ativação por teclado (Enter/Space) envia clientX:0/clientY:0; o
  // fallback via getBoundingClientRect calcula o centro do botão para que
  // a revelação radial se origine do toggle, não do canto superior esquerdo.
  const rect = event.currentTarget.getBoundingClientRect();
  const x = event.clientX || rect.left + rect.width / 2;
  const y = event.clientY || rect.top + rect.height / 2;

  document.documentElement.style.setProperty('--vt-x', `${x}px`);
  document.documentElement.style.setProperty('--vt-y', `${y}px`);

  // setTheme é síncrono — o next-themes escreve atributo + localStorage
  // em um tick. startViewTransition captura o snapshot ANTIGO, executa o
  // callback e então anima para o NOVO.
  document.startViewTransition(() => {
    setTheme(next);
  });
};
```

O guard `typeof document === 'undefined'` era para o caminho SSR. O Next.js renderiza componentes client também no servidor, e `document` não existe lá. Sem o guard, a verificação de `startViewTransition` lançaria um ReferenceError no Node.js.

O fallback de coordenadas para teclado foi o detalhe que quase esqueci. Quando alguém chega ao toggle com Tab e ativa com Enter ou Space, o navegador dispara um clique com `clientX: 0` e `clientY: 0`. Sem o fallback, a revelação sairia do canto superior esquerdo do viewport, o que parecia quebrado em qualquer layout onde o toggle não estivesse ali. O fallback via `getBoundingClientRect` calcula o centro do botão, que é para onde o usuário de teclado está olhando.

As propriedades customizadas eram definidas em `document.documentElement`, o elemento `<html>`, logo antes de `startViewTransition`. O navegador lê os valores durante a animação CSS, depois que o snapshot foi tirado e o callback rodou. A atribuição é síncrona dentro da task, então as propriedades sempre estavam definidas antes de a animação começar.

## Por que removi

O redesign de outubro de 2026 trocou os dois temas por uma paleta fixa: ink, paper e um azul signal, alternando por seção. Com uma paleta só não sobrou nada para alternar, então o toggle, o CSS de View Transitions e o componente saíram na mesma mudança. O orçamento de movimento do site foi para um campo de cubos em Three.js atrás do hero no desktop, e no lugar da troca de tema o header agora tem um controle que pausa toda animação em loop.

O que eu reaproveitaria é o andaime, não a revelação. Qualquer transição de site inteiro, como troca de rota, entrada de modal ou painel deslizando, pode usar o mesmo wrapper `startViewTransition` com a mesma detecção de feature e a mesma checagem de movimento reduzido. Navegador sem a API recebe a troca instantânea, quem pede movimento reduzido recebe um fade curto, e o resto recebe a animação. Os keyframes são a parte que muda; o JavaScript em volta continua igual.
